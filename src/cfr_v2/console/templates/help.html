Use a new set of procedures

  1. Take a snapshot of the folder of procedure PDFs. Give it the previous snapshot so unchanged PDFs aren't read again. Read its log's checks before going on.
  2. Build its LightRAG store, from the snapshot's job page (Next). It takes hours and about three gpt-5 calls per section; it resumes if stopped.
  3. Make a release with the new snapshot, from the build's job page (Next), then commit the new file with git.
  4. On Releases, Make current the new release: new cases are admitted under it from then on.
  5. Restart the worker once the runs queued under the old release are done: a worker serves one snapshot.

Run a few cases through the pipeline

  1. Admit synthetic cases (no customer data), or a list of case numbers. Nothing calls a model yet.
  2. Check the queue on System: a worker takes every queued run, not only yours.
  3. Start a worker with a small cap on queued runs. It calls the models for every run.
  4. Follow them on Cases; each case shows its timeline and every stage's result.
  5. Stop the worker from its job page when they're done. It finishes the cases it holds first.

Try the models on cases, outside the workflow

  1. Run the C02 and C03 trial on a few admitted cases. It writes nothing to the database; the form counts its model calls.
  2. From its job page, Route these claims (Next) to try C04 on the same claims, and download routing.xlsx to judge.
  3. Review files hold case text: keep them on this machine, and delete the jobs once reviewed.

Start over on new cases, leaving earlier runs behind

  1. Make a release based on the current one, with the same pins and a new id. Commit the new file with git.
  2. On Releases, Make current the new release. Pipeline and Cases show only the release new cases use; All releases shows every run.
  3. Cancel the queued runs of the earlier releases, so a worker can start. Nothing is deleted: their results stay, for labelling gold sets.
  4. Admit the new cases, check the queue on System, then start a worker.

Find out why something failed

  1. Start from Needs attention on the Pipeline page: failed jobs, blocked releases and failed case runs, each with a link.
  2. A failed job's page opens with Why it failed: the error, what it usually means and what to do; Run again reopens its form.
  3. A failed case's page shows its last error and timeline; Trace and Logs open the run in Grafana.

The stages

Admitted
C01 intake: the case was read from the source and queued under the current release. No model has seen it yet.
C02 understanding
Pass 1 lists the customer's allegations, requests and the agent's statements from the redacted transcript; Pass 2 turns them into claims, with the account, the time window and the evidence each one needs.
C03 selection
Chooses the primary claim: the one the customer most wants put right.
C04 routing
Sends each claim to one vertical (the team or product area that owns it), from the vertical definitions and the procedure sections LightRAG finds.
C05 planning
The investigation plan. A placeholder for now.
Plan ready
Every stage finished.

Words

Case run
One pass of one case through the pipeline. A case can have several, under different releases.
Release
A file in registry/releases/ naming the stage versions, the procedure snapshot and the knowledge document a run is processed with. Each run keeps the release it was admitted under.
Snapshot
The procedure PDFs, extracted, redacted and stored together, named by a sha256: ref.
LightRAG store
The search index built from one snapshot, in the folder lightrag_store_ and the start of the snapshot's hash. C04 searches it.
Knowledge document
The definitions of the verticals, published as a ref for a release to pin. It stays out of git.
Vertical
Where a claim is routed: one of the areas the knowledge document defines.
Worker
The process that takes queued runs through the stages. It refuses to start over runs whose release doesn't match the code.
Lane
Batch or realtime: a worker can serve either or both.
Job
One command started from the console, with its log and files under var/console/jobs/.
INTERNAL, RESTRICTED
How stored data is classified. The console shows INTERNAL results; RESTRICTED data (transcripts, source records) is never shown.
